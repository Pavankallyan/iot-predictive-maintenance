# IoT Predictive Maintenance

During my three years testing IoT devices, I saw the same pattern repeatedly:
a smart hub dies in the field, and the post-mortem shows the warning signs were
in the telemetry for days — drifting vibration, creeping temperature — but
nobody was watching. This project is the watcher: an unsupervised anomaly
detection system that flags smart-home hubs heading for failure, days in
advance, from their sensor streams.

## Approach
1. **Synthetic sensor data** (`src/generate_data.py`): 25 smart hubs, hourly
   temperature / vibration / power readings for 60 days. 8 devices develop
   faults with realistic signatures — bearing wear (vibration drifts up
   exponentially over ~5 days), overheating (intermittent spikes, then sustained
   heat), power faults (erratic draw with dropouts).
2. **Windowing** (`src/preprocess.py`): 24h trailing windows (6h step), 15
   features per window — per-sensor mean/std/min/max plus trend slopes, so the
   model sees both level shifts and drifts.
3. **Model**: Isolation Forest trained *only* on healthy windows (unsupervised —
   no fault labels used in training, like the real world where failures are
   rare). Operating point tuned for recall: in maintenance, a missed failure
   costs far more than a false alarm.

## Results (on the synthetic data)
| Metric | Score |
|---|---|
| Precision (prefailure windows) | 0.14 |
| Recall (prefailure windows) | 0.97 |
| F1 | 0.25 |
| Failures caught | 8/8 |
| Mean detection lead time | 68h (~2.8 days) |

The precision/recall tradeoff is the honest reality of unsupervised anomaly
detection: it catches nearly every prefailure window, at the cost of false
alarms. Detection requires a *sustained* alert (two consecutive flagged
windows) so single-window blips don't page anyone. The 68-hour average lead
time is the number that matters — nearly three days to schedule a replacement
before the device dies.

## Project structure
```
├── src/
│   ├── generate_data.py   # synthetic sensor streams + fault log
│   ├── preprocess.py      # 24h windowing + feature engineering
│   ├── train.py           # train Isolation Forest, report metrics
│   └── infer.py           # score new readings, print alerts
├── requirements.txt
└── README.md
```
`data/` and `models/` are generated by the scripts and git-ignored.

## How to run
```bash
pip install -r requirements.txt
python src/generate_data.py   # data/sensor_readings.csv + data/faults.csv
python src/train.py           # train + metrics + models/anomaly_model.pkl
python src/infer.py           # alerts: python src/infer.py [readings_csv]
```

## Design decisions
- **Why unsupervised:** labeled failures are scarce in production; the model
  must learn "normal" and flag deviations. This matches how I'd actually
  deploy it against a CloudWatch-style telemetry stream.
- **Why Isolation Forest over an autoencoder:** 15 tabular features, fast to
  train, no GPU needed, and the anomaly scores are easy to threshold and
  explain to an ops team.
- **Why sustained alerts:** single-window anomalies include sensor glitches;
  requiring two consecutive windows cut noise without hurting recall.
- **The precision caveat is documented, not hidden:** the contamination
  threshold is one knob, and I report the full tradeoff so the operating
  point can be re-tuned per device fleet.
